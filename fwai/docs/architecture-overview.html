fwai 架構解剖

fwai 是一支 TypeScript ESM 的 CLI，把「AI agent 迴圈」包進一層韌體工程專用的 護欄與證據殼裡。它的核心主張不是「讓 AI 會寫韌體」，而是 讓 AI 動硬體這件事變成可稽核、可阻擋、可重播的流程。

100TS 模組
11.1k原始碼行數
29測試檔
8架構分層
2執行路徑

一般的 AI coding agent 的迴圈是：模型要求呼叫工具 → 執行 → 回傳結果 → 再問模型。 fwai 保留了這個迴圈（src/agents/agentic-loop.ts），但在它外面多綁了四樣東西： 一組用 YAML 宣告的韌體工具（build / flash / monitor）、一個會在燒錄前擋下來的 策略引擎、一份每次執行都落地的證據檔，以及一條給 CI 用的 非互動路徑與明確的離開碼。

下面十節從外往內拆：先看整體分層，再看兩條執行路徑怎麼分岔，接著三張狀態機說明實際的執行語意， 最後談這套設計買到了什麼、以及它現在還缺什麼。

八層各自負責什麼

每層列出實際檔案，方便對照 fwai/src/ 讀原始碼。

01 Entry入口

三個入口共用同一個 AppContext：載入 config / project / tools、初始化 provider、決定 interactive 還是 ci 模式，並注入一支 confirm()。REPL 版的 confirm 用行佇列實作， 避免管線輸入時卡死。

cli.ts · repl.ts · utils/run-mode.ts · vscode-fwai/
02 Routing路由

斜線指令直接查表；自然語言走三層意圖解析：完全比對 → skill 的 triggers 關鍵字 → 交給 LLM 分類並回傳 0–1 的信心值。信心 ≥ 0.8 直接執行，≥ 0.6 先問一句，再低就退回自由對話。

commands/index.ts（22 支指令）· skills/intent-resolver.ts
03 Execution執行

Skill runner 跑宣告式流程，步驟只有四種型別：tool、evidence、 llm_analyze、agentic。Agentic loop 跑模型自主迴圈。 Orchestrator 用 semaphore 把多個 agent 併發起來，預設 3 條。

skills/skill-runner.ts · agents/agentic-loop.ts · agents/orchestrator.ts · agents/context-manager.ts
04 Tools工具

兩套工具在這裡合流。core/runner.ts 執行 YAML 宣告的韌體工具（會逐行比對開機 pattern、命中就提早收工）；ToolRegistry 管理 LLM 可直接呼叫的工具，並支援 scope 收窄、 MCP 遠端工具註冊、以及 pre/post hook。

core/runner.ts · tools/tool-registry.ts · tools/bash.ts · tools/shell-escape.ts · core/mcp-manager.ts
05 Provider模型

統一介面把 Anthropic 的 tool_use 協定當成內部標準格式，OpenAI 的 function calling 在 provider 內轉譯過來。實際實作只有這兩家（config schema 雖然列了 gemini / local， factory 會 fallback 回 anthropic）。

providers/provider.ts · anthropic.ts · openai.ts · provider-factory.ts · utils/retry.ts
06 治理Governance

三個獨立的閘門：變更預算（超過檔數/行數就擋，CI 模式離開碼 4，並用 LLM 建議怎麼拆 patch）、保護路徑（minimatch 比對）、flash guard（燒錄要人點頭， CI 要 --yes，離開碼 3）。組織策略可以由上而下覆寫專案策略。

core/policy.ts · core/org-policy.ts · core/hooks.ts · schemas/config.schema.ts
07 基礎設施Infra

與真實硬體和外部世界打交道的部分：GDB 批次執行與 backtrace 解析、OpenOCD、OTA 打包/部署/回滾、 board farm、MCP over stdio、SBOM（CycloneDX）、npm 供應鏈稽核、插件安裝。

core/gdb-session.ts · openocd-session.ts · ota-manager.ts · board-farm.ts · sbom-generator.ts · supply-chain.ts · plugin-loader.ts
08 資料Data

每次執行開一個 .fwai/runs/<run-id>/，裡面有 evidence.json、每個工具的 log、 diff.patch，選配 SBOM 與 Ed25519 簽章。寫入前會先跑一次秘密掃描把 API key 遮蔽掉。

core/evidence.ts · evidence-signer.ts · secret-scanner.ts · audit-export.ts · session-store.ts
04

兩條執行路徑

這是整個架構最關鍵的一刀：同一個輸入，可能走宣告式流程，也可能走自主迴圈。

多數 AI coding 工具只有一條路：什麼都丟給模型自己想。fwai 刻意保留了第二條—— 宣告式 skill。「build → flash → monitor → 寫證據」這種每天跑二十次、 步驟固定、失敗要有明確離開碼的工作，不需要模型每次重新推理一遍；它應該是一個 YAML 檔， 在 CI 裡零 token 成本地跑完。模型只在真的需要判斷時才被叫進來。 

# .fwai/skills/bringup.skill.yaml — 一條 skill 就是一份可版控的流程
name: bringup
triggers: ["bring up", "燒錄"]
steps:
  - tool: build      on_fail: abort
  - tool: flash      on_fail: abort   # guard.require_confirmation → CI 需 --yes
  - tool: monitor                     # 逐行比對 boot pattern，命中就結束
  - action: evidence
    summary: true

06

狀態機二：工具程序生命週期

這是韌體場景真正吃虧的地方——序列埠監看程式不會自己結束。

一般 agent 的 bash 工具假設「指令會跑完然後回傳」。韌體不是這樣：monitor 會一直吐 UART，openocd 會常駐，而你要的其實是「看到 System Ready 這行字就算成功、就可以收工了」。core/runner.ts 的狀態機專門處理這件事。

07

狀態機三：Evidence 生命週期

一次執行留下什麼、以什麼順序留下。

.fwai/runs/20260814-2210-bringup/
├── evidence.json   # 工具結果 · 開機狀態 · git 狀態 · token 用量 · 簽章
├── build.log
├── flash.log
├── monitor.log
└── diff.patch
08

這套設計買到了什麼

五個好處，每個都對應到上面某一層具體的機制。

好處機制沒有它會怎樣
不會把板子燒壞 治理 flash 工具帶 guard.require_confirmation；CI 模式必須 --yes，否則離開碼 3。另有 require_build_success 檢查上一次 build 有沒有成功。 模型「順手」跑一個燒錄指令，把錯的 image 寫進去，硬體變磚，而且沒人知道是哪一次做的。
改動有上限 治理 build 前檢查 git diff --numstat，超過檔數/行數上限就擋（CI 離開碼 4），並用 LLM 建議怎麼拆成多個 patch。保護路徑用 minimatch 比對。 一次對話下來動了 40 個檔案，review 不動，只能整包退回。
每次執行都可追溯 證據 evidence.json 記錄工具指令與離開碼、開機是否成功、diff、git commit、操作者、token 用量與估算成本；可簽章，可匯出成 SARIF 進資安流程。 「上週那次燒錄到底跑的是哪個 commit？」沒有答案。功能安全稽核（ISO 26262 / DO-178C）過不了。
固定流程不燒 token 執行 Skill 是宣告式 YAML，fwai run bringup --ci --yes 可以完全不呼叫 LLM 就跑完整套 build→flash→monitor。 每天跑二十次的例行流程，每次都讓模型重新推理一遍，慢、貴，而且結果不穩定。
模型懂這塊板子 執行 每次 LLM 呼叫都注入 project context：MCU 型號、架構、flash/RAM 大小、編譯器版本、git 分支。Agent 還能限定可寫路徑與可用工具。 模型建議一段吃掉 200 KB RAM 的寫法，而這顆 MCU 只有 128 KB。
09

跟現在直接用 Claude 有什麼不同

核心迴圈是一樣的。差別全在迴圈外面那一圈。

先把話說清楚：fwai 沒有取代 Claude，它就是拿 Claude 當引擎 （providers/anthropic.ts 用的是官方 SDK 與原生 tool_use 協定）。 問「差在哪」其實是在問：把通用 agent 換成領域專用 agent，多出來的是什麼。答案是下面這張圖裡的那圈外殼。

面向直接用 Claude（通用 agent）fwai
工具集 通用：檔案讀寫、搜尋、shell。硬體操作要靠模型自己拼指令。 同一批通用工具，外加 YAML 宣告的韌體工具（build / flash / monitor），帶逾時、開機 pattern、guard 設定。
危險操作 權限模式統一套用，不分「改一行註解」和「燒錄」。 逐工具設定：flash 一定要人點頭；CI 沒帶 --yes 直接以離開碼 3 收場。
紀錄 對話歷史 + git commit。 結構化 evidence.json：離開碼、開機是否成功、耗時、硬體狀態、token 成本，可簽章、可匯出 SARIF。
CI 需要另外包一層腳本。 原生：fwai run <skill> --ci --yes --json，離開碼 0/2/3/4/5/7 各有定義，還有全域看門狗。
領域知識 靠 CLAUDE.md 之類的說明檔，模型自己記得多少算多少。 每次呼叫強制注入 MCU / 架構 / flash / RAM / 編譯器版本，不依賴模型記憶。
模型綁定 綁 Anthropic。 LLMProvider 介面抽象，Anthropic 與 OpenAI 都能跑，換 provider 不動上層。
成熟度 成熟產品，工具鏈與生態完整。 0.1.0，自建專案。覆蓋面窄，但那一小塊窄的地方（韌體安全與稽核）是通用工具不會做的。

一句話總結

通用 agent 優化的是「讓模型能做更多事」；fwai 優化的是 「讓模型做的每件事都能被擋下、被記錄、被重播」。 在只會弄壞原始碼的場景，前者夠用；在會弄壞一塊 3000 元的板子、或需要通過功能安全稽核的場景，就需要後者。

10

誠實的限制

讀架構圖之前該知道的三件事。

簽章驗證已改為信任存放區模式（已修）

舊版的 verifyEvidenceSignature() 是拿證據檔裡自帶的那把公鑰驗自己的簽章， 只能證明「檔案沒被改過」，不能證明「是誰簽的」——攻擊者改完內容用自己的金鑰重簽，驗證照樣通過。

現在拆成兩個獨立判斷：integrity（簽章與內容相符）與 trusted（簽章金鑰在信任清單裡）， 兩者都成立才算 valid。信任清單來自 .fwai/keys/trusted/ 或 security.signing.trusted_keys；沒有設定清單時只做完整性檢查，且 valid 恆為 false。 src/core/evidence-signer.ts

文件與程式碼有落差

倉庫裡的 fwai/docs/architecture.md 描述了 Gemini / Ollama provider、 KB 語意搜尋、/mcp 與 /kb 指令——這些檔案目前不存在於 src/。 本頁的內容一律以實際程式碼為準。
